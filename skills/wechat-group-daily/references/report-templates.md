# 按群选择日报模板

每个群每天仍生成一份日报，模板不改变关注群和采集窗口。模板与视觉主题 `theme` 分开。

| 模板 | 用途 | 内容 |
| --- | --- | --- |
| `detailed` 详细版 | 回顾完整讨论（默认） | 依照 [写作规范](writing-spec.md) 整理话题、故事线、人物与引用 |
| `project` 项目工作版 | 工作群同步 | 今日总结、任务与交付物、责任人、期限、群内进展、阻塞与后续节点 |

## 配置与生效范围

在 WorkBuddy 对话中确认各群用途后，从 Skill 的 `scripts` 目录执行：

```powershell
python fetch.py report-template list
python fetch.py report-template set --chat "<稳定群ID>" --template project
# 恢复详细版：同一命令使用 --template detailed
```

设置写入包外配置的 `chats[].report_template`，保留其他配置；旧配置默认详细版。用户无需手动编辑 JSON。
新采集的归档冻结模板，`daily` 的待出报条目返回 `report_template`。写稿按归档字段选择流程。
已有归档、待出报稿和历史日报保持原模板；普通 `archive --date` 重采沿用该日原模板。更改设置作用于之后新采集的归档，不会立即重写今天的日报。
同日空／不足窗口若按现有 `daily --reopen` 重新采集，会使用新设置；已经出报的窗口不重发。

## 项目工作版写作流程

1. 读完冻结归档；用 `fetch.py analyze --chat "<稳定群ID>" --date <YYYY-MM-DD>` 获取可引用的 `source_id`。分析输出可能截断，只用来查 ID，不能代替完整归档。
2. 先总结今天涉及哪些工作，再逐项提取明确布置的任务、责任人、期限、进展、阻塞与后续节点。相同任务合并，保留变更和最终口径；相互冲突的消息写入待确认并保留双方来源。
3. 责任人只写原文明示的人，不能把发言人自动当责任人。未知责任人／期限用 `null`，页面显示“待确认”；期限不明确时保留原话，不猜具体日期。无依据的进展用 `null`。
4. 任务状态只用 `已布置`、`群内反馈已完成`、`存在阻塞`、`待确认`。有人说完成，只代表群内反馈；不能推断已经验收。提议与讨论不写成已布置任务，放在待确认或后续节点。
5. 每条总结和任务绑定支持该结论的 `source_ids`。只引用文字及成功的语音转写；图片、未转写语音及附件占位不是工作事实。语音识别内容需核对，未处理内容由页面标明。
6. 短通知、一条明确任务也可以出报，不套用详细版的字数、段数、人物卡要求。无工作事项时可简述“本时段未识别到工作事项”，绑定可读来源，任务等数组留空；没有任何可读文字时维持素材不足。
7. 写下方结构，执行 `check_story.py`，修正错误后用 `render_daily.py` 渲染，再 `daily --finish`。后台交付遵循 [定时任务说明](scheduling.md)。

## 项目稿结构

以下为虚构示例。`username/date/source_revision` 必须替换成待出报条目值，`source_ids` 必须替换为本归档来源 ID。

```json
{
  "username": "demo@chatroom",
  "group_name": "示例项目群",
  "date": "2026-10-27",
  "source_revision": "<冻结归档的 collection.revision>",
  "report_template": "project",
  "lead_title": "方案提交与联调安排",
  "project": {
    "summary": [
      {"text": "今天明确了方案提交安排，联调时间仍待确认。", "source_ids": ["message_0:101", "message_0:102"]}
    ],
    "tasks": [
      {"title": "提交接口方案", "owner": "小林", "deadline": "明天下午前",
       "progress": null, "status": "已布置", "source_ids": ["message_0:101"]}
    ],
    "progress": [],
    "risks": [
      {"text": "联调日期尚未明确。", "source_ids": ["message_0:102"]}
    ],
    "next_steps": []
  }
}
```

`summary` 至少一条，其他数组可空或省略；每组最多 100 项，每项 1—30 个来源 ID。
任务 `title` 必填，`owner/deadline/progress` 为文字或 `null`，`status` 省略时显示待确认。
其他条目的 `text` 必填。检查器验证结构、可读来源 ID 与版本绑定；结论是否被原文支持仍由模型与人工核对。
页面顺序为总结→任务→推进→阻塞→后续节点，每项可展开原文依据。项目版不显示叙事人物分析面板。

## Windows 验收（待实际执行）

- 两个测试群分别设置两种模板。下一次新采集后核对 `daily` 返回模式、冻结归档、稿件、阅读页与历史索引；旧稿不受切换影响。
- 项目群只发一条简短任务，责任人或期限缺失：仍能成报，缺失字段显示待确认；篡改来源 ID／版本或模板应被验稿与渲染阻止。
- 验证任务合并、期限变更、完成反馈和冲突提示；核对原文展开及手机窄屏。纯图片／失败语音不编造内容，混合消息标明缺失范围。
- 编辑原有定时任务，替换 [完整提示词](scheduling.md#可直接复制的每日任务提示词)。后台生成和再次运行都不弹网页／窗口，只返回结果链接；手动双击桌面入口能打开阅读页。
- 重启 WorkBuddy 后核对任务提示词仍已保存、只有原有一条任务；到点运行单独验收。更新文件不会自动修改 WorkBuddy 已保存的任务。
