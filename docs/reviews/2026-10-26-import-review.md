# 微信群日报导入、闭环与初始化审查

日期：2026-10-26（Asia/Shanghai）。对象：用户提供的 1.2.0 工作区、分发包与完整备份。

## 结论

**已有可用的功能骨架，正常路径能串起来，但还没有达到“朋友初始化后，每天可靠自动出报”的闭环。**

- 采集、按日期与群归档、模型稿件检查、HTML/PNG 渲染、本机浏览都有实现。
- 本轮用合成数据跑通归档 → 实际 HTML 渲染 → 登记 → 重建索引，并实际查看了浏览台。
- 初始化只设置时间，没有创建、校验或迁移 WorkBuddy 定时任务；失败处理、数据完整性与分发审计仍有缺口。
- 19 项本地探查中，13 项复现了缺陷触发条件，其余 6 项通过或有明确边界。这不是“13 台实际机器出错”，也不是 Windows 端到端验收。
- 本轮只导入、审查和保存复现证据，没有修改旧实现、安装依赖、运行取密钥程序、创建定时任务或上传 GitHub。

## 3. 初始化流程是否合理

**顺序总体合理，完成条件不合理。** 先检查环境、确认账号、定路径，再取密钥、解密、选群是可行顺序。本人决定选群、非交互时不默认选择账号，以及未初始化业务命令退出 6，这些边界值得保留。

当前第七步叫“定时”，实际只把字符串写入 `collect.schedule` 和 `compose.time`，没有驱动执行。`setup.py` 最后的“初始化完成”最多说明写好了配置，并不证明首份日报成功，更不证明每天会自动运行。

建议将完成状态拆清楚，流程到以下证据齐备才宣称可日常使用：

1. 环境兼容且依赖可用；明确 Windows 与已验证的微信版本范围。
2. 用户确认微信账号、外部数据目录和关注群；失败重跑不清掉旧的有效配置。
3. 所需核心库解密成功，消息可读，缺失覆盖明确报错。
4. 采集一个指定日期，对每个群得到“成功有消息 / 成功无消息 / 失败”的结果。
5. 模型生成首份稿件、自检通过、HTML 可打开；PNG 若降级则明确记录。
6. 在 WorkBuddy 创建或核对定时任务，回读触发时间与提示词，并完成一次试运行。
7. 打开浏览台，能看到预期日期、全部关注群、日报与失败原因。

第 6 步可以由宿主 Agent 完成，不必硬塞进 Python；但需要明确的创建/校验入口和可恢复记录。朋友拿到包后不能依赖原机器上已有的定时任务。

## 4. 功能闭环判定

| 用户目标 | 现状 | 闭环判断 |
|---|---|---|
| 关注多个群 | 有配置与选群向导，档案与索引有群 ID | 有实现；同名、改名与歧义路径需要修复 |
| 每天自动出日报 | HANDOFF 记录两条 WorkBuddy 任务；代码包只有时间配置 | 原机器任务存在性与后续成功记录未核验；新机器初始化不闭环 |
| 每个群每日总结 | 归档、写作规范、自检、渲染、登记均有 | 正常 HTML 路径已测；模型产稿与内容完整性未作实际验收 |
| 按群、日期回看 | 最近、日期、群、详情、矩阵、搜索都有 | 浏览正常路径可用；搜索过滤、重新采集后的链接、空记录状态存在 bug |
| 失败后恢复 | 有 doctor、退出码、可重建索引 | 无持久运行日志、统一任务状态、明确重试/补跑机制；部分失败会被掩盖 |
| 给朋友/团队使用 | 有 setup、doctor、package | 缺依赖声明和第二台 Windows 演练；定时任务不随包安装；审计仍有盲区 |

`paths.logs` 仅创建和显示，没有业务模块写运行日志；`archive.cleanup()` 没有接入主流程。`initial_days`、`overlap_days` 是配置字段，当前没有对应的自动补采执行逻辑。不能把配置存在视为功能已实现。

## 7. 建议处理顺序

1. **先保障数据正确与原文件可恢复**：F01/F02/F03/F07，稳定群 ID、按分片映射、完整性与失败闸门。
2. **再闭合初始化和自动运行**：F04/F05/F06/F11，首份出报验收、宿主定时任务注册校验、运行日志与补跑。
